# Rust dependency updates

Use architecture section 18, especially 18.3 and 18.5–18.10. Package/version register
is retained research, not installed/qualified graph or permission for defaults.
Without Cargo, produce requested research/admission proposal; create no workspace
or installed packages merely to update skills. Existing task authorization controls
actual updates.

Inspect branch/HEAD, staged/unstaged/untracked ownership, manifests, Cargo.lock,
toolchain/MSRV/edition, target/features, patches, git sources, Cargo configuration
and build/tool policy. Preserve work, lockfile and receipts. Use owned isolated
candidate when updates conflict with another worker's graph/tests. Never
reset/stash/overwrite or expose registry credentials.

Record baseline graph identity, enabled features, runtime/build/proc-macro/native
components, advisory database revision and findings. Research bounded cohort against
primary release notes, manifests/source, security policy, Windows support and
license grants. Separate patch/minor/major/zero-major, prerelease and git-source
changes; SemVer proves no behavioral/license compatibility.

Before resolution, decide cohort and visible holds. Re-evaluate affected Serde/parser
behavior, TLS provider/trust/licensing, NTS packet AEAD and Win32/service boundaries.
Preserve held/optional candidates. Neither replace selected validation model nor
admit TUF from research without concrete design decision.

The owner's revised DEC-18 selects garde 0.23.0 for shared pure DTO/settings
validation inside mandatory private construction. Admit it with defaults disabled
and only `derive` initially; inspect the resolved graph and feature unification
before adding rules/features. It is no longer an optional settings experiment.
Run the [contract enforcement](../../implementation/implement-rust-contracts/references/contract-enforcement.md)
fixtures for field coverage, actual constructor invocation, bypasses, finite
values and bounded errors. Selection does not claim an installed or qualified
application graph; retain the no-scaffolding rule when Cargo source is absent.

Use [Cargo operations and evidence](references/cargo-operations.md) for scoped
resolution, feature/source inspection and qualification. Review whole lockfile delta,
including unexpected transitives; preserve justified patches and explain changes.
New build scripts/proc macros/native compilation execute code: review provenance
before build, not only runtime-crate audits afterward.

After the intended resolution/acquisition, use the
[configured-tool workflows](../../testing/references/configured-tooling.md) for
applicable pinned format/compiler/Clippy/rustdoc, selected tests/build and graph
checks on the final target/feature rows. Keep the final analysis frozen; dependency
updates themselves are explicit resolution operations, not frozen checks.
Run configured cargo-deny for the selected graph rows; any selected complementary
cargo-audit supplies lockfile advisory evidence, not a feature-row graph check.
Use admitted RustSec/index snapshots with verified refresh receipts no older
than 24 hours. Missing acquisition/freshness evidence remains incomplete; never
silently fetch during frozen analysis or suppress inherited findings.

When the dependency-review policy applies, use admitted cargo-vet for the exact
final graph through the guide's
[analysis lane](../../testing/references/configured-tooling.md#additional-rust-analysis).
Missing reviews remain a blocking policy result, separate from advisory/license
checks. Preserve canonical audit data; use an owned writable store copy and
verify its full entry/byte inventory before and after even locked checks.
Never manufacture audits, imports or exemptions to clear an update.

Add causal parser/protocol/Windows tests
where changed guarantee requires; no blind expensive-gate campaign. Advisory/license
checks need actual graph/fresh database; shared-database tools provide no independent
assurance.

Report admitted versions/checksums/origins/features/license grants, reasons, holds,
transitive delta, old/new findings, executed checks and Windows/release evidence gaps.
Separate inherited failures. Dependency maintenance implies no staging, commit,
signing, publication or release.
