# Protected persistence and aggregate work

Use architecture sections 6, 10–12 and the task's actual operation guarantee. Name the canonical writer, source/installed/policy/cache/journal class, authorized fixed path/handle, schema/version, ACL, current revision/generation and recovery owner. User UI preferences, optional drift priors and mandatory broker security journals have different failure policies.

Separate admission, candidate preparation, validation, staging write/sync, publication, durable state and acknowledgement. An error return alone establishes no rollback boundary. Prove the intended late stage is reached after a valid no-fault control. Observe original/published bytes, authoritative revision, journal progress, owned staging artifacts and next permitted action. Publication can succeed before acknowledgement fails; reconcile the authoritative state before retrying or claiming nothing changed. A generic rename or `fsync` call alone does not prove the required Windows filesystem/power-loss guarantee.

Check path/handle use against traversal, Windows drive/share/device forms, reparse points, replacement races, inherited rights and open-handle sharing as relevant. Confine fixtures to owned temporary locations. OS ACL/path tests require native execution; an input string allowlist cannot establish a hardened filesystem sandbox. Do not log sensitive path contents to demonstrate rejection.

Resource bounds need an owner and aggregate accounting: per-frame and per-field limits, clients/in-flight tasks, queued and completed work, retained source histories/snapshots/caches, nested crypto/parser work, diagnostics and task replacements. Checked arithmetic or a fixed-capacity container cannot by itself bound total process memory/work. Determine whether counts are bytes/characters/elements and whether sleeping, abandoned or cancelled work remains live.

Cancellation requested, result invalidated, operation completed, task exited and resources released are distinct observations. A dropped handle is not a join, and unwinding cannot catch every abort/OOM or undo an external effect. Keep hostile/resource cases within owned process/host limits and record peak/cumulative work when making that claim. Restore owned fault dependencies and perform only a bounded recovery; successful retry does not erase the first failure or cleanup cause.

Use exact raw bytes at the challenged parser seam. Generic JSON maps collapse duplicate keys and replacement-decoded text hides malformed UTF-8. Pair hostile cases with valid neighboring records and inspect forbidden state/effects, not error wording alone. Miri/sanitizers, where supported and selected, observe specific executed paths; neither proves native OS behavior, soundness of every FFI path or aggregate hostile-input safety.
