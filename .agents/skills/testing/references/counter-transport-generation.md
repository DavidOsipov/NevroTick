# Keep counter identity separate from expected truth

Use when positional counter fields drift across maintained Rust/Python test
instrumentation. Prefer a small named enum/record if it removes synchronization
work without a generator. A registry earns adoption when maintaining several
representations justifies its cost; start with one counter family and assess the
result. This is test-only infrastructure, not adoption of product schema generation
or another runtime validation engine.

## Own only mechanical representations

A small closed, versioned registry may own field identity, transport spelling/order,
numeric representation and explicit categories. It may generate named Rust
identifiers/formatters and Python typed mappings/parser definitions. Keep case
recipes, source-work coefficients, numerical reference facts, resource allowances,
rejection expectations and qualification decisions independently authored.
Reserved upper bounds, observed attempts, transport completeness and assertion
outcomes remain distinct even when their records share mechanical definitions.

Validate unique identities/names, exact shape, permitted types and bounded size.
If JSON is chosen, detect duplicate keys before ordinary dictionary normalization;
the default Python decoder keeps the last repeated name. Preserve declared count
semantics across languages: Python integers need explicit bounds and boolean
rejection for Rust `u64` counts. Keep explicit zero fields, required cardinality,
overflow checks and the format's actual duplicate/unknown-field policy.

Version the producer/reader contract when order, identity or meaning changes.
A registry-only version cannot identify an old emitted record. Bind the actual
transport or its admitted surrounding envelope to the appropriate version; decide
coordinated rejection or compatibility with retained consumers/receipts. Never
silently reinterpret historical evidence under a new mapping.

Generate reviewable files during development. Frozen verification checks exact
expected generated bytes and fails on stale/tampered output; it does not rewrite
the candidate. Admit registry, generator, inputs and generated outputs in the
applicable closure. Keep generation deterministic and acquisition explicit;
avoid adding `build.rs` or a new execution layer without a concrete need.

## Challenge shared mistakes independently

- Retain an independently written raw row with distinct sentinel counts and an
  independently specified mapping to names. An emitter/parser round-trip can pass
  with both sides using the same wrong registry mapping.
- Deliberately swap a field mapping and require that independent observation to
  fail. Exercise omitted, duplicate, unknown, reordered and invalid-valued fields
  according to the declared format; retain valid zero and range-boundary controls.
- Change a generated file and require check-only generation to reject it.
  Qualify generator/configuration changes through the existing harness controls;
  generation does not make field meanings or source-work bounds correct.
- Preserve partial/missing observations as incomplete. A complete transport row
  cannot replace reserved work, a native exit/assertion or a qualification decision.

Reuse [harness qualification](harness-qualification.md) and
[typed verification interfaces](python-verification-typing.md). Keep concrete
schema decisions and execution receipts in the existing task under its applicable
CHECK-6/19/25 obligations; this reference supplies no measured maintenance benefit.
