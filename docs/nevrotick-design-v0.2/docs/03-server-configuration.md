# NevroTick v1 — ручная настройка серверов времени

**Дата:** 28 октября 2026 года.  
**Редакция дизайна:** 0.2.  
**Статус:** UX и контракт данных для проектирования; нативная реализация и системные испытания отсутствуют; UI-прототип и его ограниченные проверки описаны в отчёте QA.  
**Область:** только клиент синхронизации времени NTPv4/NTS. DNS-модуль в этот документ не входит.  
**Архитектурный источник:** [windows-time-architecture.md, revision 1.4](../references/source-docs/windows-time-architecture.md).

Уточнения basic UI взяты из [RWTC-FEATURES-001 revision 1.0](../references/source-docs/windows-time-features.md), исходный статус **Proposed**. Архитектура 1.4 остаётся авторитетной для селекции, полномочий и доверия; новая презентация не заменяет runtime-проверки.

## 1. Как читать требования

В документе используются три обозначения:

- **АРХ** — требование исходной архитектуры 1.4; UX должен его сохранять.
- **UX** — предложенный способ представить это требование в интерфейсе. Он не расширяет полномочия сервисов или набор протоколов.
- **OPEN** — поведение или точные пределы, которые ещё должны быть зафиксированы и проверены при реализации.

Ручное добавление сервера и явный выбор NTS/NTP входят в запрос пользователя. Поддержка произвольных плагинов, DNS-протоколов, PTP, refclock, удалённого управления и автоматического обновления через TUF здесь не предполагается. Отдельный update-assessment остаётся оценкой кандидата, а не принятым решением об updater.

## 3. Окно Add time server / Edit time server

### 3.1. Основные поля

| Элемент | Предлагаемое представление | Значение |
| --- | --- | --- |
| **Protocol** | Обязательный раскрывающийся список | `NTS — authenticated NTPv4` или `NTPv4 — unauthenticated` |
| **Server address** | Обязательное текстовое поле; ввод с клавиатуры и вставка | DNS-имя, IPv4 или IPv6; одна идентичность на строку источника |
| Подпись для NTS | `NTS-KE server` | Показывает, какой сервер пользователь вводит |
| Сводка подключения | Текст под адресом | Протокол транспорта и эффективный порт; для NTS также автоматическое согласование endpoint времени |
| **Advanced** | Свёрнутая по умолчанию группа | Дополнительные параметры из §5 этого документа |
| Основные действия | **Add to draft** / **Save to draft**, **Cancel** | Сохранение меняет черновик; применение машинной политики выполняется отдельно |

**UX:** при создании нового источника предлагается NTS. В NTP-only профиле интерфейс может предварительно выбрать NTP, но выбор остаётся видимым. При редактировании сохраняется фактическое значение протокола, без автоматического преобразования.

NTS в этом списке означает защиту NTPv4 средствами Network Time Security. Отдельные варианты `SNTP`, `NTPv3`, `TCP time` и `HTTPS time` не добавляются.

Под кнопками или рядом с индикатором изменений используется понятная подпись: **“Review and apply pending changes to update the service.”** Она отделяет сохранение черновика от действующего состояния сервиса.

### 3.2. Два этапа NTS и смысл порта

NTS-KE устанавливает ключи через TLS 1.3 или новее на TCP-порту 4460. Затем NTP-пакеты передаются по UDP. Сервер NTS-KE может согласовать другой адрес и UDP-порт для времени; при отсутствии соответствующих записей используются IP-адрес NTS-KE-сервера и UDP 123. [R1, §§3–4, 4.1.7–4.1.8]

| Выбранный протокол | Изменяемый порт | Подпись по умолчанию |
| --- | --- | --- |
| NTS | **NTS-KE port: 4460** | `Key establishment: TCP 4460. Time endpoint is negotiated automatically.` |
| Plain NTPv4 | **NTP port: 123** | `Time requests: UDP 123. Replies are unauthenticated.` |

UDP 123 — стандартное назначение NTP; иной порт может использоваться согласно локальной политике. [R2, §§7.2, 9.1]

**UX:** редактирование порта находится в Advanced, а эффективное значение видно сразу. В режиме NTS нельзя подписывать 4460 как общий “Time port”.

После установления ассоциации в подробностях доступны поля только для чтения: **Configured NTS identity**, **NTS-KE endpoint**, **Negotiated time endpoint**. Пользователь не обязан вручную заполнять второй адрес для NTS. Прямое переопределение согласованного NTP endpoint в этом дизайне v1 не вводится.

## 4. Ввод адреса и ошибки

### 4.1. Синтаксис

**АРХ:** идентичность сервера не является произвольным URL, файловым путём или командой. Нормализация выполняется по правилам конкретного типа; отображаемая подпись не подменяет идентичность (§6.2).

**UX:** поле принимает только имя узла либо IP. Протокол и порт задаются собственными элементами управления. Схема URL, путь, query string, userinfo и несколько адресов в одном поле приводят к понятной ошибке. Приложение не пытается молча извлечь сервер из произвольной строки.

Для IPv4 используется строгая десятичная запись из четырёх компонентов. Неоднозначные сокращённые, шестнадцатеричные и восьмеричные формы не принимаются как IP. Ошибочный IP-подобный ввод не должен неожиданно превращаться в запрос к DNS-имени.

Для IPv6 предпочтителен адрес без квадратных скобок: порт находится в отдельном поле. Прототип также принимает адрес в скобках и явно показывает каноническую идентичность без них; запись [IPv6]:port отклоняется.

При поддержке IDN выполняется выбранная реализацией IDNA-нормализация. Пользователь видит итоговую ASCII-идентичность рядом с международным именем. TLS-проверка DNS-имён использует нормализованные A-labels; IP проверяется как IP-идентичность сертификата, включая точное соответствие `iPAddress` subjectAltName. [R3, §§6.1, 6.3–6.4]

**OPEN:** точный IDNA-профиль, обработка завершающей точки, коротких LAN-имён, окружающих пробелов и вручную заданных IPv6 scope identifiers должны быть зафиксированы в едином сетевом контракте. Они не получают случайные разные трактовки в UI и сервисе. Делегированные NTS-адреса отдельно подчиняются формату RFC 8915, §4.1.7.

### 4.2. Примеры

Примеры ниже показывают синтаксис и предлагаемые сообщения. Адреса не являются рекомендациями провайдеров и не проверялись на доступность. Корректная форма не доказывает доверие или разрешение сетевого назначения.

| Ввод | Результат на уровне формы |
| --- | --- |
| `time.example.net` | Допустимая форма DNS-имени |
| `192.0.2.10` | Допустимая форма IPv4; примерный адрес, не рабочий сервер |
| `2001:db8::10` | Допустимая форма IPv6; примерный адрес, не рабочий сервер |
| `192.168.1.10` | Допустимая форма LAN IPv4; применение требует разрешённой сетевой области |
| `bücher.example` | При принятой поддержке IDN отображается также `xn--bcher-kva.example` |
| Пустое поле | `Enter a server name or IP address.` |
| `https://time.example.net/` | `Enter a host name or IP address, without a URL scheme or path.` |
| `time.example.net:4460` | `Enter the port separately in Advanced.` |
| `[2001:db8::10]` | Принимается с явно показанной нормализацией в `2001:db8::10`; порт задаётся отдельно |
| `time.example.net/path` | `A server address cannot contain a path.` |
| `user@time.example.net` | `Enter a server name or IP address without user information.` |
| `server-a.example, server-b.example` | `Add each server separately.` |
| `999.1.2.3` | `Enter a valid IPv4 address.` |
| `127.1` или `0x7f000001` | `Use a full dotted-decimal IPv4 address.` |
| Порт `0`, `65536`, `-1` или `44.60` | `Enter a whole-number port from 1 to 65535.` |

Диапазон порта `1–65535` — предлагаемое ограничение приложения. Допустимость конкретного порта и конечного назначения дополнительно определяется машинной политикой.

### 4.3. Формат, доступность и доверие — разные результаты

| Ситуация | Где и как сообщать |
| --- | --- |
| Ошибка синтаксиса | Под полем; фокус переводится к первому ошибочному полю при попытке Save |
| Имя не разрешается | Состояние сохранённого источника: `Name resolution failed`; форма адреса не объявляется неверной |
| Истёк сетевой тайм-аут | `Server did not respond`; показываются последняя попытка и следующий повтор |
| Сертификат не соответствует имени/IP | `Server identity could not be verified`; NTS остаётся NTS, автоматического перехода на NTP нет |
| Неизвестная цепочка доверия или иная ошибка проверки | Конкретная причина проверки и доступное действие; без кнопки обхода |
| Назначение запрещено политикой | `Destination is not allowed by the configured network policy` |
| Дата непригодна для выбранного verifier | Явное состояние Recovery/Blocked с объяснением; без молчаливого исправления диапазона даты |

**АРХ:** private/LAN-источники поддерживаются при явном разрешении. Все фактические назначения, включая NTS-делегирование и повторное DNS-разрешение, проверяются по сетевой политике (§7.4). Нельзя глобально запретить LAN только ради упрощения формы.

## 5. Advanced: только предусмотренные параметры

| Поле | Предлагаемый контракт |
| --- | --- |
| **NTS-KE port / NTP port** | Отдельное целое значение; смысл зависит от протокола. При смене протокола сброс к стандартному значению видим пользователю |
| **Display name** | Необязательная подпись. Не меняет адрес, сертификатную идентичность или независимость источника |
| **Operator group** | Явная группировка источников одного оператора. Неизвестная группа не объявляется доказанно независимой |
| **Time scale** | В прототипе только `UTC — unsmeared`. Другие шкалы и варианты leap smear не предлагаются без отдельного решения |
| **Polling policy** | Справочная информация о действующей политике. Basic UI v1 не предлагает произвольные индивидуальные интервалы или oscillator/step/rate tuning |

**АРХ:** шкалы времени разных провайдеров нельзя смешивать без согласованной политики; тип шкалы не определяется достоверно по одному пакету (§10.5). В текущем дизайне ограничение одним вариантом `UTC — unsmeared` является **UX-выбором прототипа**, а не утверждением о характеристиках любого введённого сервера.

Поля TLS identity override, пользовательские сертификатные исключения, выбор алгоритма AEAD, ручное назначение Main, числовой “trust score”, pool expansion и переключатель `Ignore certificate errors` отсутствуют.

## 6. Черновик, профиль и применение

### 6.1. Редактирование без эффекта на систему

**UX:** Add/Edit работает с черновиком настроек. **Add to draft / Save to draft** возвращает к списку с обозначением неприменённых изменений; изменённая строка имеет метку **Draft**. Cancel закрывает редактор без сохранения его новых изменений. До завершения Apply сервис продолжает использовать последнюю принятую конфигурацию.

### Отображение ролей и состояния черновика

| Внутренний смысл или прежняя подпись fixture | Видимая подпись v0.2 | Условие |
| --- | --- | --- |
| Principal | **Main** | Источник выбран алгоритмом как основной |
| Supporting | **Supporting** | Допущенный совместимый supporter |
| Rejected | **Not used** | Источник не участвует; короткая понятная причина видна в строке |
| Pending — неприменённое изменение | **Draft** | Служба ещё не приняла эту версию записи |
| Применённая запись без достаточных текущих данных | **Waiting** | Конфигурация принята; измерения или селекция ещё не завершены |

Названия не являются новой wire-schema или переименованием алгоритмических состояний. **Waiting** не используется для неприменённого Draft. После Apply новая или изменённая запись переходит к Waiting; прежняя оценка не выдаётся за измерение новой конфигурации. Main/Supporting/Not used назначаются только по последующим действительным результатам селекции. Аутентифицированный NTS-ответ может иметь роль Not used, если его оценка расходится с другими.

Проверка совместимости источника выполняется относительно **выбранного профиля черновика**. Если профиль не менялся, он совпадает с действующим профилем сервиса.

При несовместимом протоколе сохранение в черновик заблокировано. Под полем Protocol видна причина и переход в **Settings** с сохранением незавершённого черновика формы:

> Plain NTP sources cannot participate in the selected NTS-only profile. Change the synchronization profile in Settings before saving this source.

Симметричное сообщение применяется к NTS-источнику в выбранном NTP-only профиле. Выбор протокола не переключает весь профиль самостоятельно.

### 6.2. Смена профиля

Пользователь явно меняет желаемый профиль в Settings. Смена появляется в черновике и обзоре изменений. Все несовместимые строки помечаются; **Apply** блокируется, пока список источников не приведён в соответствие с новым профилем и другими инвариантами.

Интерфейс не создаёт скрытых профилей, не переписывает протоколы у остальных серверов, не превращает несовместимые источники в bootstrap helpers и не скрывает их удалением. Пользователь редактирует или удаляет строки осознанно.

До Apply проверяются структурные инварианты: канонические идентичности, дубликаты, совместимость профиля/шкалы времени, допустимые пределы и достаточное число настроенных логических записей для возможности выполнить выбранную политику. Такая проверка **не устанавливает реальную eligibility, доступность, аутентификацию, независимость или согласие серверов**.

При работе движка одновременно выполняются **оба** условия: установленный минимум согласующихся текущих eligible identities **и** правило строгого большинства в популяции, допущенной до проверки согласия, согласно квалифицированному алгоритму селекции. Нельзя заменить это условием «в списке достаточно серверов» или создать большинство, заранее исключив несогласные записи только ради положительного результата. Две из четырёх настроенных строк сами по себе не доказывают успешный выбор.

В basic v1 **single-source mode отложен**; он не предлагается настройкой и не включается при удалении/отказе серверов. Будущее введение такого режима потребует отдельного явного решения и evidence, а не уменьшения ограничения текущим UI.

### 6.3. Review → Apply → результат

| Шаг | Поведение |
| --- | --- |
| **Review changes** | Показывает добавленные, изменённые и удалённые источники; смену профиля; эффективные порты; влияние на аутентификацию |
| **Apply** | Заранее обозначает требование прав администратора и запускает стандартный путь авторизации конкретного изменения |
| Повторная проверка | Привилегированная сторона проверяет собственный актуальный статус, права, входные данные и ожидаемую ревизию политики |
| Успех | Новая конфигурация становится действующей. Новые/изменённые источники — Waiting до достаточных текущих данных; “Applied” не означает “Synchronized” |
| Отмена UAC | Действующая конфигурация не меняется; черновик остаётся доступен для дальнейшего редактирования |
| Конфликт ревизий | Данные перечитываются; пользователь видит, что конфигурация изменилась, и повторно просматривает изменения |
| Ошибка применения | Отображается причина; запрещён частично применённый набор, который выдаётся за успешный |

**АРХ:** авторизация, ревизии, повторная серверная валидация и сохранение предыдущего состояния при отказе определены §§4–6. Точное расположение Review и Pending changes — **UX-предложение**.

## 7. Контракт данных: смысл полей

Это семантическая модель для дизайна и последующей реализации, а не новая утверждённая JSON-схема. Имена wire-полей, enum-значения, обязательность необязательных полей и числовые пределы утверждаются при P1.

| Значение | Семантика и ограничения |
| --- | --- |
| Идентификатор источника | Стабильный, назначаемый приложением; не зависит от отображаемого имени |
| Протокол | Только предусмотренные режимы NTS/NTPv4; нельзя подменять логикой “auto” |
| Каноническая идентичность | Проверенное DNS-имя либо IP; используется для сравнений и эффектов, а не только для показа |
| Настроенный порт | NTS-KE TCP-порт либо NTP UDP-порт согласно протоколу |
| Отображаемая подпись | Необязательные пользовательские данные, отделённые от идентичности |
| Группа оператора | Явная модель зависимости источников; отсутствие знания не равно независимости |
| Шкала времени | Для прототипа `UTC — unsmeared`; согласована с политикой набора |
| Политика опроса | Наследуется из утверждённой политики; числовые инварианты проверяются принимающей стороной, raw override не входит в basic UI |
| Ревизия конфигурации | Изменение связано с ожидаемой ревизией; устаревший черновик не получает автоматического приоритета |

**АРХ:** границы декодируют ограниченные строгие записи, строят проверенные доменные значения и отдельно проверяют актуальную авторизацию/состояние (§6). Неизвестные поля, неоднозначные представления, неверные типы и некорректные комбинации не должны превращаться в разрешающие значения по умолчанию.

**OPEN:** точные длины полей, число символов label/group, лимиты ошибок, IDNA-нормализация и окончательные допустимые интервалы ещё не фиксируются этим UX-документом. Архитектурные проектные бюджеты — до 16 логических источников и до двух bootstrap helpers; P1 должен закрепить полную таблицу пределов. Это ограничения проекта, а не числа из протокольного стандарта.

## 8. Recovery: отдельная настройка bootstrap helpers

В Recovery используется отдельная группа **Bootstrap time hints — plain NTP**. Она выключена в строгом профиле и включается администратором. Для каждого helper предусмотрены ручной адрес и NTP UDP-порт; протокол здесь фиксирован как plain NTP с явной подписью **Unauthenticated**.

Вместо общего “Backup server” интерфейс объясняет назначение:

> Used only to help establish authenticated time when the system date prevents certificate validation.

**АРХ:** helper даёт только временную оценку даты для изолированной проверки сертификатов. Его показания не входят в обычную NTS-селекцию и сами по себе не разрешают запись системных часов. Одно- и двухсерверная политики различаются явно. Потеря второго helper не ослабляет требование автоматически (§§8.1–8.4).

В ходе восстановления показывается, что используются неаутентифицированные подсказки и системные часы на этом этапе ещё не изменены. Причина сертификатной ошибки, невозможность проверить дату, конфликт подсказок и отсутствие сети не объединяются в одно сообщение “Sync failed”.

Новая оговорка revision 1.4 о диапазоне verifier (§18.7.2) сохраняется: недопустимую дату нельзя молча ограничить допустимым максимумом или переполнить в другую дату. Конкретные границы выбранного адаптера остаются предметом квалификации OPEN-8.

## 9. Чего нет в интерфейсе v1

### Непроверенный сервер и кнопка Test

Публичный refresh не принимает адреса и работает с существующей конфигурацией (§§4.2, 5.3). Поэтому в этом UX-контракте **нет сетевой кнопки Test для произвольного несохранённого endpoint**. Локальная проверка формата не обращается к сети.

Путь пользователя: ввод → проверка полей → Save в черновик → Review → Apply с авторизацией → получение данных сервисом. После применения доступен обычный refresh в пределах принятой конфигурации. Отдельный сетевой тест нового endpoint потребовал бы новой явно авторизованной операции и не вводится одним макетом.

### Пулы

Архитектура не определяет отдельный пользовательский тип Pool или совместимость с директивой chrony `pool`. Поэтому нет селектора Server/Pool, автоматического превращения DNS-ответов в независимые голоса и обещания поддержки NTS для произвольного pool hostname. Обычное DNS-разрешение и замена endpoint сохраняют идентичность логического источника.

### Гарантии безопасности

NTS подписывается как аутентификация времени, а не как гарантия правильного UTC или полной конфиденциальности. Plain NTP подписывается как **Unauthenticated**. Совместимость legacy NTP в revision 1.4 отдельно требует решения об исключении по entropy в OPEN-9/S0.7; интерфейс не выдаёт её за полное соответствие ASVS.

## 10. Минимальные сценарии проверки будущей реализации

Это план проверки, а не выполненные тесты.

1. Ввод NTS hostname и изменение NTS-KE порта не меняют смысл UDP endpoint времени.
2. Выбор plain NTP в NTS-only черновике блокирует Save и объясняет переход к Settings.
3. Смена профиля не применяется до устранения несовместимых источников; протоколы строк не переписываются автоматически.
4. Отмена UAC и конфликт ревизий сохраняют действующую конфигурацию.
5. Корректный адрес с неподходящим сертификатом остаётся ошибкой доверия; перехода к NTP нет.
6. Разрешённый LAN-сервер принимается при соответствующей политике; запрещённое назначение отклоняется и после повторного DNS-разрешения.
7. Согласованный NTS endpoint/порт виден в диагностике и проходит отдельную проверку назначения.
8. Bootstrap helper не появляется среди обычных голосующих источников; двухсерверная политика не ослабляется при отказе одного.
9. Валидация Unicode/IDN/IP и ошибок порта совпадает в UI и принимающем компоненте.
10. Ошибки доступны с клавиатуры и через UI Automation; поля и протоколы имеют однозначные озвучиваемые имена.
11. Структурно достаточный черновик с недоступными, недопущенными или несогласными источниками не становится Tracking после Apply; реальная селекция требует и configured eligible agreement minimum, и строгого большинства.
12. Новая запись показывается как Draft до Apply и Waiting после применения до свежих результатов. Internal Principal/Rejected отображаются как Main/Not used, с причинами; single-source режим недоступен.
