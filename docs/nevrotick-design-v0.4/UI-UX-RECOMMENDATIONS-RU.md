# NevroTick v0.4 — два режима и частота синхронизации

**Дата:** 5 ноября 2026 года. **Для:** David Osipov.

**Основание:** текущая правка владельца — предыдущий интерфейс перегружен; нужны минималистичный Simple и информативный Power user, а в Settings — периодичность синхронизации времени. Исходная база проекта: commit `8a66af924c509e898a9bab9bb3282f11b24fba93`. v0.4 поставляется отдельным автономным прототипом.

## Решение

Созданы **два представления одной модели данных**. Simple открыт по умолчанию; переключатель постоянно доступен в шапке. Он меняет плотность информации, сохраняя состояние, доверительную политику, черновики и настройки.

Основная причина перегрузки v0.3 — подробности экспертного анализа одновременно присутствовали на повседневном экране: основания доверия, несколько возрастов данных, коррекция, календарь UTC, восстановление, управляющие элементы макета. В v0.4 эти подробности доступны в Power user, а инструменты просмотра сценариев свёрнуты по умолчанию.

Это дизайнерская оценка по структуре и исходникам. Наблюдение пользователей и визуальная проверка текущего HTML в браузере не проводились.

## Simple

Две вкладки: **Status** и **Settings**. Начальный Status состоит из одной содержательной секции:

- название состояния и короткое объяснение;
- понятная маркировка доверия;
- оценка расхождения часов с направлением ahead/behind и неопределённостью;
- последний подтверждённый time check;
- следующий шаг либо объяснение автоматической работы.

Отдельных карточек Evidence, Clock activity, UTC calendar и Recovery на этом экране нет. Персонаж не занимает повседневный Status. Оригинальный wordmark сохранён. При нормальной работе нет необходимости открывать технические разделы.

При ошибке пользователь получает краткое последствие и **What can I do?**. Диалог объясняет следующий шаг и позволяет явно перейти в Power user. Большая коррекция, истёкшее предложение и неизвестный результат открывают соответствующий разбор; недоступные системные операции не становятся активными кнопками.

### Какие различия сохранены

| Состояние | Смысл в Simple |
| --- | --- |
| NTS и явный NTP | NTP виден как **Unauthenticated NTP**. |
| Observe only | Измерение работает, изменения часов отключены профилем. |
| Holdover | Используется прежняя модель; свежего согласия нет. |
| Истёкшая оценка | Числовая текущая оценка скрыта, новые коррекции приостановлены. |
| Источники расходятся | Аутентификация не подменяет согласие; коррекции приостановлены. |
| Потеря связи со статусом | Текущее состояние службы неизвестно; прежние значения не выглядят свежими. |
| Подтверждённая остановка | Синхронизация недоступна из-за остановки службы. |
| Конфликт владельца часов | Измерения не дают права менять часы; переход ведёт в Time policy. |
| Большая коррекция | Предложение требует проверки и ещё не применено. |
| Неизвестный исход | Изменение могло произойти; перед повтором нужна сверка результата. |
| Будущее восстановление | Явная метка Future design; происхождение unauthenticated date hint сохраняется после NTS. |

Эти различия следуют из текущей модели проекта и ранее исправленных fixtures. Упрощение не отменяет их. Канонические основания: [Architecture §§8–11, 16](https://github.com/DavidOsipov/NevroTick/blob/8a66af924c509e898a9bab9bb3282f11b24fba93/docs/windows-time-architecture.md), [F-03/04/07/08](https://github.com/DavidOsipov/NevroTick/blob/8a66af924c509e898a9bab9bb3282f11b24fba93/docs/windows-time-features.md).

## Power user

Сохранены подробные Status, Sources, Diagnostics, Settings, Date recovery и About. Добавлена **Statistics**:

1. Offset, uncertainty, согласие источников и количество согласующихся групп операторов.
2. Сравнительный график последних доступных наблюдений источников. Точка — offset, отрезок — offset ± uncertainty. Роли различаются цветом, формой маркера и текстом таблицы.
3. Числовая таблица: источник, оператор, offset, uncertainty, роль, последний valid reply и последнее принятое измерение.
4. Контекст: возраст снимка, квалифицированная оценка, референсный интервал, подтверждённая коррекция и отдельно локальное предпочтение частоты.

График использует имеющиеся поля `sources[].offset` и `sources[].uncertainty`. Разные измерения имеют разные возраста: это последние наблюдения внутри одного status snapshot, а не синхронный замер. Отрезки не объявлены 95% confidence intervals или гарантией точности UTC. Для большой коррекции шкала явно увеличивает область наблюдений; таблица сохраняет точные миллисекундные значения.

В конфликте источников текущие спорные интервалы доступны, даже если общая оценка историческая. При stale подпись относится к последнему полученному снимку. `null` не превращается в нулевое отклонение. В holdover показывается сохранившаяся модель, но новые интервалы источников не выдумываются.

Временные графики, RMS, RTT, jitter, uptime, процент точности и прогноз исчерпания holdover не добавлены: для них отсутствуют измерительные ряды. Основание — поля `BASE`, `BASE_SOURCES`, преобразования `deriveSources()` и разделение `historical` / `sourceHistorical` в комплектном `src/model.js`.

## Sync frequency

Настройка есть в обоих режимах:

| Элемент | Поведение |
| --- | --- |
| Automatic (recommended) | Исходный выбор макета; ручное указание периода не требуется. |
| Custom | Показывает предпочтительный интервал: 2, 5 или 15 минут. |
| Update preview | Сохраняет локальное предпочтение. |
| Cancel | Возвращает сохранённый выбор; фокус направляется обратно в поле частоты. |
| Sample timing & service policy | В Power user отдельно показывает факты сцены и локальное предпочтение. |

Краткое пояснение внутри приложения: **Controls time checks. Recovery and server limits may change the actual interval.**

Это предпочтение периодичности измерений. Оно не выдаёт разрешение переводить часы по каждому таймеру, не сбрасывает backoff, не обходит серверные ограничения и не изменяет NTS-политику. В HTML выбор не перезаписывает образец «Next scheduled check in 40 s» и не имитирует успешное применение службой. При потере связи фактическое расписание неизвестно, при остановленной службе — недоступно.

F-02 требует, чтобы обычный пользователь не был обязан подбирать polling interval. Опциональная настройка с Automatic этому не противоречит. Архитектура описывает общий ограниченный scheduler и стартовый диапазон 64–1024 секунд; 120/300/900 секунд выбраны как примеры внутри него. **Это предложение пресетов, а не принятие production default/min/max.** Реальная валидация и применение остаются за машинной политикой сервиса. Основания: [F-02, F-05, F-06](https://github.com/DavidOsipov/NevroTick/blob/8a66af924c509e898a9bab9bb3282f11b24fba93/docs/windows-time-features.md), [Architecture §§6.3, 7.3, 12.2, 17](https://github.com/DavidOsipov/NevroTick/blob/8a66af924c509e898a9bab9bb3282f11b24fba93/docs/windows-time-architecture.md).

## Непрерывность работы

Смена Simple / Power user сохраняет сценарий, source drafts, поиск и фильтры, выбранную секцию Settings, сохранённую и несохранённую частоту. Выход с Power-only страницы открывает Simple Status, а возврат восстанавливает прежнюю Power-страницу. Settings остаётся общей страницей.

Открытый редактор не теряет незаполненный ввод из-за смены режима: mode switch недоступен, reducer игнорирует такой переход, а приложение не перерисовывает no-op. Локальное добавление источника не меняет активное согласие или количество голосов.

Смена демонстрационной сцены сохраняет режим и частоту, очищая source drafts. Полный сброс возвращает Automatic и исходную сцену, сохраняя режим. Перезагрузка страницы сбрасывает всю локальную память.

## Независимая проверка и исправления

Два субагента подготовили рекомендации и затем проверили новый код:

- **UX:** разделение двух режимов, информационная плотность, сценарии ошибок, навигация, черновики и взаимодействия.
- **Архитектура:** смысл частоты, requested versus effective scheduling, источники данных для Statistics, историчность и свежесть.

По проверке исправлены: неподтверждённое «Active schedule: Automatic» при недоступной службе; возвращение отменённого manual interval после Cancel; адресат фокуса после исчезновения Cancel; слишком широкая историческая подпись, затрагивавшая локальное предпочтение; переходы к политике, открывавшие Synchronization; технические формулировки следующего шага в Simple.

Отчёты с disposition находятся в `review/`. История v0.3 отделена в `review/baseline-v0.3/` и не считается проверкой новой сборки.
