## Existing producer, new state and consumer

Current owners are [`ntp-wire`](../crates/ntp-wire/Cargo.toml), which exposes
`frame_no_legacy_mac_datagram`, immutable `RawHeader` and exact `NtpTimestamp`
parts, and [`time-domain`](../crates/time-domain/Cargo.toml), which exposes
checked coordinates/windows, `unfold_ntp`, exact arithmetic and distinct clocks.
Neither currently owns an outstanding request or certifies a saved T1's origin.

The new flow is:

1. The driver supplies an explicit fixture source/socket/endpoint binding,
   generation tuple and separately saved send coordinate, token and monotonic
   readings. These are asserted fixture facts, not OS-established identity.
2. The association privately retains a fully admitted pending request.
3. `receive` takes complete packet bytes and actual receipt facts supplied by
   that driver; it frames the bytes, checks association/currentness/correlation,
   stages a control or numerical result, then completes the current slot once.
4. The driver observes the public result and the owner's subsequent behavior.
   It cannot construct a completed result from a raw header or bypass the slot.

Current configuration/binding/generations belong to the association, not to
packet fields or a caller-provided `authenticated`, `fresh` or `current` boolean.
The future adapter must establish the actual receipt/send/clock-mapping facts.
Typed numeric facts in this pure owner cannot certify that adapter's truth.

## Private inputs, state and boundary contracts

Names here specify responsibilities; final spelling may change without changing
meaning. Every representation is private and immutable except the exclusive
association owner. No raw public fields, mutable-inner getter, unchecked raw
conversion, permissive `Default` or public completed-result factory is allowed.
`Association` and its pending state implement neither `Clone` nor `Copy`.

Use bounded numeric fixture IDs rather than attacker-sized text. Distinct source,
socket, generation and request types retain units/roles; constructors may accept
already checked `NonZeroU64` identities. Those identities certify representation,
not administrator approval, uniqueness across processes or actual socket ownership.
An endpoint is an explicit `std::net::SocketAddr`; no hostname parsing/resolution.
Use `UtcCoordinateQ32`, `EraWindow` and `MonotonicNs` directly for their existing
guarantees. No UTC/active-awake reading may substitute for a monotonic deadline.

`WireToken` is a distinct private nonzero 64-bit representation. Its sole raw
constructor `WireToken::new(u64)` rejects zero and admits every value in
`1..=u64::MAX`, with no normalization, fallback, entropy or freshness claim.
`arm` accepts this checked type, not an unrestricted raw integer. The receive
path constructs the same checked type from raw origin bits before comparison;
direct handler calls cannot make a zero origin match a pending nonzero token.
No public field, unchecked `From`, mutation or `Default` may bypass construction.

## Ordered receive and completion rules

The only supported profile is a named **plain-header fixture profile**. It uses
`FrameLimits::new(48, 0)` and complete framing before header access. A longer
packet is outside this experiment, even when the S1.1b framer could structurally
parse it under different explicit limits. No extension, legacy MAC or NTS profile
is inferred; this is not a shipped UDP limit or downgrade fallback.

Check supported version 4/server mode 4 and the actual pending association before
interpreting packet content. Check source/socket/exact endpoint, captured versus
current configuration/association/clock generations and local mapping generation,
then checked nonzero origin and exact token equality. No alternate source lookup
or endpoint rebinding is driven by response bytes. Timing must satisfy
`send <= arrival <= processing_now < deadline`; a packet queued before a deadline
but processed at/after it fails. The future adapter owns monotonic truth and
continuity; the pure wrapper does not prove either.

Classify stratum zero separately under the resolved fixture control rule below. For a
time candidate require LI in 0..=2, stratum in 1..=15 and nonzero receive and
transmit wire timestamps. Preserve other raw quality claims without qualifying
them. Unfold T2 and T3 through their explicit numeric windows and calculate with
the **saved real T1**, peer T2/T3 and local T4. Packet origin never substitutes for
saved T1. Preserve odd Q33 half-ticks and signed Q32 RTT, including negative RTT.
Do not silently round/narrow the result or apply statistical admission policy.

Complete only after every applicable guard/transformation succeeds, with one
current-state owner and no reentrant user code. A successful time result removes
the pending request once. The same response thereafter produces no second result.
Malformed, unsupported, uncorrelated, stale, expired or numerically invalid traffic
does not consume a pending request. Explicit trusted cancellation/expiry/context
changes are intentional retirement transitions, not packet-rejection effects.

`UnauthenticatedFixtureObservation` is not `ValidatedSample`, authenticated time,
eligibility, a vote or correction authority. Root properties, reference time,
precision/frequency error and chronology/quality thresholds remain unqualified.
The later statistical owner must admit the actual complete observation and current
policy before creating a sample; it cannot infer eligibility from this type name.

### Exact observation fields and retention

The private time-observation result exposes these exact, bounded facts:

- Source ID, socket ID, exact endpoint, request ID, committed configuration/
  association/clock generations and checked receipt mapping generation.
- Monotonic send, arrival, processing and deadline readings; saved real T1,
  unfolded peer T2/T3 and local T4 coordinates; exact Q33 offset and signed Q32 RTT.
- Raw quality claims: LI (`u8`), stratum (`u8`), poll (`i8`), precision (`i8`),
  root-delay bits (`u32`), root-dispersion bits (`u32`), reference ID (`u32`) and
  reference-timestamp bits (`u64`). Preserve wire bits/signs; no quality threshold,
  uncertainty, reference-era, reference-age or eligibility inference is added.

Store these named fields, not a retained `RawHeader`, `RawDatagram`, full packet,
origin token or packet slice. The request token lives only in the pending slot and
temporary checked comparison; completion/retirement drops it. No rounded-i64
nanoseconds or hidden residual loss is introduced. The later statistical owner
receives the enumerated raw claims plus checked facts and must independently admit
their complete policy/meaning before constructing an eligible sample.

A control result retains only its opaque reference-ID code and bounded source/
socket/endpoint/request/generation/monotonic timing facts. It retains no peer T2/T3,
four-timestamp arithmetic, packet/header/token or time-quality observation.

### Resolved fixture choice S1.1d-Q1: once-only correlated stratum-zero control

**Resolved by the D-REV-1 revision as an explicit fixture choice.** After complete
framing, v4/server profile, current binding/generations, deadline and checked
nonzero-origin correlation pass, a stratum-zero reply produces one opaque control
event and terminally consumes the request. This applies to every LI value 0..=3;
LI synchronization and nonzero T2/T3 rules apply only to time candidates. Do not
unfold, inspect for validity, retain or calculate with control T2/T3. It produces
no time result, statistics update, automatic rearm, poll change, blacklist or
network work. Unknown reference-ID codes remain opaque; recognizing `RATE` creates
no scheduler. A duplicate after completion produces no second control or time
result. Uncorrelated/stale/expired/zero-origin controls preserve pending state and
produce no control event.

[RFC 5905 §7.4](https://www.rfc-editor.org/rfc/rfc5905.html#section-7.4) identifies
stratum-zero reference IDs as control codes and requires discarding KoD receive/
transmit timestamps because their values are undefined. The explicit fixture
choice enforces that separation and architecture §7.3's no-time-sample rule.
CHECK-6 and the [source-readiness response/state row](s0.1-source-readiness.md#selected-upstream-ledger-and-observed-flow)
motivate one terminal event per current request. The existing `kod-rate` literal
has **LI=0** and remains unchanged: it must be control-only, not become a rejected
time candidate merely because a comparator uses a different KoD classifier.

This deliberately differs from pinned Chrony 4.9 `ntp_core.c` at
`8df4f1263e206585e6c4e61352d042c2dd12916a` (retained SHA-256
`ca206410bddc03c56996bba2bddbca2ab01029f9c5b619d4a55025f37d8c4ac0`):
[lines 2029–2087](https://github.com/mlichvar/chrony/blob/8df4f1263e206585e6c4e61352d042c2dd12916a/ntp_core.c#L2029)
classify `kod_rate` only for RATE/stratum-zero/LI-unsynchronized after test1/2/5;
test1 also examines peer timestamps. Its separate `valid_packet` includes test3's
nonzero origin/receive/transmit requirements, and
[lines 2326–2335](https://github.com/mlichvar/chrony/blob/8df4f1263e206585e6c4e61352d042c2dd12916a/ntp_core.c#L2326)
set `valid_rx` only for a `valid_packet`. This card instead classifies every fully
correlated stratum-zero fixture as opaque control independently of LI/T2/T3 and
completes that slot once. It copies neither the RATE-only/LI classifier nor the
time-timestamp-dependent consumption predicate. Record this exact adaptation in
the future port ledger; it is not a reproduced Chrony defect or a claim that

RFC action/scheduling requirements, including RATE backoff and DENY/RSTR handling,
remain a later transport/controller integration obligation. This slice has no
polling or association-demobilization engine and makes no full NTP-client or
shipping-policy conformity claim. The terminal fixture choice is a routine bounded
implementation decision; it grants no production plain-profile/entropy exception.

### Adopted API and routine boundary choices

`lib.rs` owns the crate contract, unsafe prohibition and reexports; `context.rs`
owns immutable input representations/constructors; `association.rs` owns the
state, transitions and completed result types with private fields. There is no
separate sibling completed-result factory. Keep original module functions/types
private except the declared consumer API; no `Default` or unchecked `From`.

- Distinct `SourceId`, `SocketId`, `RequestId` wrap checked `NonZeroU64`; `new`
  accepts that type and `value` projects the scalar. Distinct configuration,
  association and clock generation types accept every u64, including zero,
  through `new`, expose `value`, and provide fallible nonwrapping `checked_next`.
- `Generations::new(configuration, association, clock)`,
  `Binding::new(source_id, socket_id, SocketAddr)` and
  `AssociationContext::new(binding, generations)` retain those named immutable
  roles with matching getters. Exact endpoint values are fixture claims.
- `WireToken::new(u64)` rejects zero; no token getter or revealing Debug output.
  `RequestTiming::new(send, deadline)` enforces positive lifetime at most one
  second using matching `MonotonicNs`; getters preserve both values.
  `PeerEraContext::new(receive_window, transmit_window)` requires actual checked
  windows and provides no absent/default context.
- `ReceiptFacts::new(binding, mapping_clock_generation, arrival, processing_now,
  local_t4)` retains asserted typed receipt facts. The receiving owner checks
  their relationships; the caller supplies no authoritative current tuple,
  accepted flag or authenticated marker.
- `Association::new_plain_header_fixture(context, initial_request)` starts empty.
  `arm(saved_real_t1, token, timing, peer_eras)` returns the allocated request ID;
  `receive(packet_bytes, receipt)` returns one `FixtureEvent`; `cancel(id)` and
  `expire(now)` return the retired ID; `advance_context(next)` returns the optional
  retired ID. Read-only projections expose current context, pending request ID
  and optional next request ID, never pending token/packet state.
- A successful arm may use request ID `u64::MAX` exactly once, atomically changing
  its next-ID state to `None`. That pending request remains usable. Later empty-
  slot arms reject exhaustion; busy rejection precedes sequence exhaustion.
  Completion/retirement never resets sequence. Every failed arm preserves it.
- Generation updates may jump forward; all components must be nondecreasing and
  at least one increases. Every binding change requires association-generation
  increase. A saturated component may remain equal while another advances;
  `checked_next` at MAX fails, and an all-MAX context has no successful advance.
- Receive stages the complete result, rechecks current request/context under
  exclusive ownership, then clears the slot with no fallible work afterward.
  `FixtureEvent::Time(UnauthenticatedFixtureObservation)` and
  `FixtureEvent::Control(OpaqueControl)` retain exactly the fields enumerated
  above. Shared private `CompletionFacts` has only read-only getters. All result
  construction stays inside the association owner; there is no public raw factory.
